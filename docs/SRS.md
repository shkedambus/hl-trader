# hl-trader

## 1. Введение

### Scope

Входит в MVP:

- отбор трейдеров HyperLiquid: сбор кандидатов, метрики, фильтры, оценка, уверенность, стиль, вердикт;
- пересчет вердиктов по сохраненным данным при смене весов и порогов;
- отслеживание позиций отобранных трейдеров и событий по ним;
- веб-рейтинг, карточка трейдера, страница методики и отчет проверки отбора;
- Telegram-бот: подписки, уведомления о сделках и пересмотре вывода;
- MCP-сервер с инструментами `find_traders`, `get_trader`, `get_trader_events`.

Не входит в MVP (из non-goals PRD):

- автоматическое копирование сделок и любые действия со счетом пользователя;
- доступ к кошельку пользователя и хранение его ключей;
- биржи, кроме HyperLiquid; мобильное приложение;
- оценка и отслеживание маркет-мейкеров и высокочастотных трейдеров;
- инвестиционные рекомендации; платные тарифы.

### Термины и сокращения

| Термин | Значение |
| --- | --- |
| Трейдер | аккаунт (адрес) на HyperLiquid, чьи публичные данные оценивает система |
| Публичный рейтинг | рейтинг биржи со стоимостью счета, прибылью, доходностью и оборотом каждого аккаунта |
| Кандидат | трейдер, прошедший предварительный отсев по публичному рейтингу |
| Сделка (круг) | позиция по одной монете от открытия до полного закрытия, включая доливки и частичные закрытия |
| Окно оценки | период, за который учитываются сделки; по умолчанию 180 дней |
| Метрика | число, рассчитанное по истории счета или сделкам трейдера |
| Фильтр | обязательное условие отбора; провал любого фильтра отклоняет трейдера независимо от оценки |
| Оценка | число от 0 до 1, взвешенная сумма нормированных метрик |
| Уверенность | число от 0 до 1: сколько данных стоит за оценкой; в оценку не входит |
| Стиль | класс трейдера по медианному времени удержания позиции |
| Вердикт | итог отбора на дату: "отобран" или "отклонен", с метриками, оценкой, уверенностью и причинами |
| Методика | действующий набор порогов, весов и формул; имеет номер версии |
| Событие | зафиксированное изменение позиции трейдера или пересмотр вывода о нем |
| Когорта | вердикты всех оцененных трейдеров на одну дату, используемые для проверки отбора вперед |
| Вес запроса | единица лимита API HyperLiquid; на IP доступно 1 200 единиц в минуту |
| MCP | Model Context Protocol, стандарт подключения инструментов к ИИ-агентам |
| FR / NFR | функциональное / нефункциональное требование |

## 2. Общее описание

### Контекст и место в продукте

Система самостоятельна и работает только с публичными данными HyperLiquid. Она решает пять задач: отбирает трейдеров, отслеживает позиции отобранных, показывает результат в вебе, доставляет уведомления в Telegram и отдает данные ИИ-агентам по MCP. Все пять используют общее хранилище метрик, вердиктов, позиций и событий.

### Пользователи

| Роль | Кто | Что делает в системе |
| --- | --- | --- |
| Частный трейдер | основной пользователь (PRD, Audience) | смотрит рейтинг и карточки, подписывается на трейдеров в Telegram |
| Разработчик ИИ-агента | вторичный пользователь | подключает агента к MCP-серверу |
| Разработчик сервиса | внутренний пользователь, автор проекта | меняет веса и пороги, запускает пересчет, следит за лимитом API и задержками |

### Допущения и зависимости

- HyperLiquid отдает публичный рейтинг, состояние счета, историю счета и историю сделок любого адреса без авторизации.
- Лимит API -- 1 200 единиц веса в минуту на IP-адрес. Он общий для всех процессов системы.
- История счета приходит редкими точками (десятки за жизнь счета), а не ежедневно.
- Отметка о ликвидации в сделке может относиться к контрагенту, а не к самому трейдеру.
- Доступны Telegram Bot API и клиенты, поддерживающие MCP.
- Пользователь Telegram сам инициирует диалог с ботом.

### Ограничения

- Работа только с публичными данными, только чтение. Ордера не выставляются.
- Все процессы вместе тратят не больше 1 100 единиц веса в минуту, а 100 единиц остаются запасом на повторы (NFR-2).
- Число одновременно отслеживаемых трейдеров ограничено бюджетом API, по умолчанию 60.
- Веб-интерфейс -- desktop браузер.

## 3. Требования

### Функциональные требования

#### Отбор и оценка

| ID | Требование | Критерий приемки |
| --- | --- | --- |
| FR-1 | Система должна не реже раза в сутки получать публичный рейтинг биржи, отбирать кандидатов по условиям предварительного отсева (А.1) и упорядочивать их по приоритету. Для аккаунтов, не прошедших отсев, система не должна выполнять запросов, расходующих вес API. | Аккаунт, нарушивший хотя бы одно условие А.1, отсутствует в списке кандидатов, и по его адресу в журнале нет ни одного запроса к API. Список кандидатов упорядочен по приоритету. |
| FR-2 | Для каждого кандидата система должна рассчитывать метрики по истории счета и сделкам за окно оценки: стаж, стоимость счета, доходность с поправкой на риск, максимальную просадку, число завершенных сделок, долю прибыльных сделок, отношение прибыли к убыткам, среднюю доходность сделки, медианное время удержания, долю ликвидированного объема, число точек истории счета, признак неполной истории сделок. | На эталонном наборе данных все метрики совпадают с ручным расчетом с точностью до 10⁻⁶. Метрика, которую нельзя посчитать (например, доходность с поправкой на риск по двум точкам), сохраняется как "нет данных", а не 0. Ликвидация засчитывается трейдеру, только если ликвидирован он сам, а не контрагент. Доходность с поправкой на риск приводится к году по фактическому среднему интервалу между точками истории. |
| FR-3 | Система должна проверять каждого кандидата по фильтрам (А.2) и отклонять провалившего хотя бы один фильтр независимо от оценки. Для отклоненного должен сохраняться список проваленных фильтров с фактическими значениями. | Трейдер, нарушивший один фильтр, получает вердикт "отклонен", и в причинах указан именно этот фильтр с фактическим значением и порогом. Трейдер с максимальной оценкой, но проваленным фильтром тоже отклонен. |
| FR-4 | Система должна вычислять оценку от 0 до 1 как взвешенную сумму метрик, нормированных линейно между полом и потолком (А.3). Метрика "нет данных" исключается вместе со своим весом, остальные веса перенормируются. Оценка трейдера не должна зависеть от других трейдеров в базе. | Для эталонного трейдера оценка совпадает с ручным расчетом, а сумма вкладов метрик равна оценке. При отсутствии одной метрики оценка считается по остальным с перенормировкой. Добавление в базу других трейдеров не меняет оценку эталонного. |
| FR-5 | Система должна вычислять уверенность от 0 до 1 по числу завершенных сделок, числу точек истории счета и полноте истории сделок (А.4). Уверенность не должна влиять на оценку. | При прочих равных трейдер с бо́льшим числом сделок имеет не меньшую уверенность. При неполной истории сделок уверенность в 2 раза ниже. Оценка одинакова у трейдеров с разной уверенностью и одинаковыми метриками. |
| FR-6 | Система должна присваивать трейдеру стиль по медианному времени удержания и числу сделок в день (А.5). | Для медиан удержания 2 мин (при >= 200 исполнений в день), 10 мин, 3 ч, 2 дня, 10 дней присвоены стили соответственно: маркет-мейкер, HFT, внутри дня, свинг, позиционный. |
| FR-7 | Система должна выносить вердикт "отобран", если трейдер прошел все фильтры, его оценка и уверенность не ниже порогов, а стиль один из трех: внутри дня, свинг или позиционный (А.6). В отслеживание попадают не более N отобранных с наибольшей оценкой. Вердикт сохраняется с датой, версией методики, метриками, оценкой, уверенностью и причинами. | Трейдер, удовлетворяющий всем условиям, отобран. При уверенности ниже порога или стиле HFT трейдер отклонен с соответствующей причиной. При 70 подходящих трейдерах и N = 60 отслеживаются 60 с наибольшей оценкой. |
| FR-8 | При изменении весов, порогов или формул система должна по команде разработчика сервиса пересчитать оценки, уверенность и вердикты всех трейдеров по сохраненным метрикам, не обращаясь к бирже. Новая версия методики сохраняется, прежние вердикты остаются в истории. | После изменения порога и пересчета вердикты соответствуют новому порогу, в журнале нет ни одного запроса к API за время пересчета, вердикты прежней версии доступны. |

#### Отслеживание и события

| ID | Требование | Критерий приемки |
| --- | --- | --- |
| FR-9 | Система должна отслеживать позиции отобранных трейдеров и создавать событие при открытии, увеличении, уменьшении, развороте и закрытии позиции. Событие содержит адрес, монету, направление, размер в долларах, плечо, тип изменения и время. | Каждое из пяти изменений позиции на эмуляторе биржи порождает ровно одно событие с правильным типом и полями. |
| FR-10 | Система должна создавать событие "вывод пересмотрен", когда меняется вердикт трейдера либо его оценка или уверенность меняются не меньше чем на 0,1. Событие содержит прежние и новые значения и причину (например, проваленный фильтр). | Трейдер провалил фильтр по ликвидациям при пересчете -> создано событие с причиной "ликвидации". Изменение оценки на 0,05 без смены вердикта события не создает. |

#### Веб

| ID | Требование | Критерий приемки |
| --- | --- | --- |
| FR-11 | Система должна показывать веб-рейтинг отобранных трейдеров: адрес, оценка, уверенность, стиль, монеты открытых позиций, дата расчета. Рейтинг сортируется по оценке или по уверенности и фильтруется по монете, стилю и минимальной уверенности. | Рейтинг содержит всех отобранных и только их, с указанными колонками. Сортировка и каждый из трех фильтров дают ожидаемый список на тестовых данных. |
| FR-12 | Система должна показывать карточку любого оцененного трейдера по адресу: вердикт; оценка и вклад каждой метрики; статус каждого фильтра с фактическим значением и порогом; уверенность и ее составляющие (число сделок, точек истории, полнота истории); стиль и медианное время удержания; открытые позиции; события; дата расчета и версия методики. Для неоцененного адреса система должна сообщать, что трейдер не оценивался. | Для отобранного трейдера все перечисленные элементы присутствуют, сумма вкладов равна оценке. Для отклоненного видны проваленные фильтры. Для неизвестного адреса показано "трейдер не оценивался", без ошибки. |
| FR-13 | Система должна публиковать страницу методики: условия отсева, фильтры, веса, границы нормировки, формулу уверенности, пороги отбора, номер версии и дату вступления в силу. | Значения на странице совпадают с конфигурацией, по которой выполнен последний расчет. После изменения методики (FR-8) на странице новая версия и дата. |

#### Telegram-бот

| ID | Требование | Критерий приемки |
| --- | --- | --- |
| FR-14 | Система должна позволять пользователю Telegram подписаться на отслеживаемого трейдера (из карточки или командой с адресом), посмотреть список подписок и отписаться (командой или кнопкой в уведомлении). На неотслеживаемого трейдера подписка не оформляется, бот объясняет причину. | Подписка из карточки и по адресу появляется в списке подписок. После отписки следующее событие трейдера пользователю не приходит. Подписка на отклоненного трейдера отклонена с причиной. |
| FR-15 | При событии из FR-9 система должна отправить каждому подписчику трейдера сообщение: адрес, действие, монета, направление, размер, плечо, стиль, оценка, уверенность, среднее время удержания, кнопки "Карточка" и "Отписаться". При уверенности ниже 0,5 сообщение содержит пометку "мало данных". | Сообщение по событию открытия содержит все поля и обе кнопки. При уверенности 0,35 пометка есть, при 0,8 ее нет. |
| FR-16 | При событии из FR-10 система должна отправить подписчикам трейдера сообщение о пересмотре: прежние и новые оценка, уверенность, вердикт и причина. | Подписчики получают сообщение с причиной, а пользователи без подписки на этого трейдера его не получают. |

#### MCP-сервер

| ID | Требование | Критерий приемки |
| --- | --- | --- |
| FR-17 | Система должна предоставлять MCP-инструмент `find_traders(coin?, style?, min_confidence?, limit?)`, возвращающий отобранных трейдеров по убыванию оценки: адрес, оценка, уверенность, стиль, монеты позиций, дата расчета. | Вызов `find_traders(coin="BTC", style="swing", min_confidence=0.5)` возвращает только трейдеров со свинг-стилем, позицией или сделками по BTC и уверенностью >= 0,5, по убыванию оценки. |
| FR-18 | Система должна предоставлять MCP-инструмент `get_trader(address)`, возвращающий карточку трейдера с тем же содержанием, что FR-12, в машиночитаемом виде, а для неоцененного адреса возвращающий статус "не оценивался". | Поля ответа для отобранного трейдера совпадают с веб-карточкой. Для неизвестного адреса возвращается статус "не оценивался", а не ошибка сервера. |
| FR-19 | Система должна предоставлять MCP-инструмент `get_trader_events(address, since)`, возвращающий события трейдера (FR-9, FR-10) после момента `since` в хронологическом порядке. | Возвращаются только события после `since`, по возрастанию времени, с полями из FR-9 и FR-10. |

#### Проверка отбора

| ID | Требование | Критерий приемки |
| --- | --- | --- |
| FR-20 | Система должна в день отбора фиксировать когорту, а через 30 дней строить для нее отчет проверки отбора: медианная доходность отобранных и не прошедших за 30 дней, их разница, доля отобранных, провалившихся по фильтрам за 30 дней. Отчеты по всем когортам публикуются в вебе; когорта, для которой 30 дней еще не прошли, помечается "проверка еще идет". | На эмулированных данных когорты отчет через 30 дней содержит обе медианы, их разницу и долю провалившихся; значения совпадают с ручным расчетом. Когорта моложе 30 дней показана с пометкой "проверка еще идет" и без цифр. |

### Нефункциональные требования

| ID | Категория | Требование | Критерий приемки |
| --- | --- | --- | --- |
| NFR-1 | Производительность | Задержка от изменения позиции на бирже до доставки уведомления в Telegram: p95 <= 30 с при 60 отслеживаемых трейдерах. | Нагрузочный тест на эмуляторе: 60 трейдеров, 200 изменений позиций, p95 <= 30 с. |
| NFR-2 | Соблюдение лимита API | Все процессы системы вместе расходуют <= 1 100 единиц веса в любую минуту. На ответ "превышен лимит" система повторяет запрос с растущей задержкой. Доля таких ответов <= 1% запросов за сутки. | Часовой прогон: расход в каждую минуту <= 1 100. При эмуляции ответа 429 интервал между повторами растет. |
| NFR-3 | Свежесть данных | Метрики и вердикты отслеживаемых трейдеров пересчитываются не реже раза в 7 дней. Дата расчета видна в карточке и в ответе `get_trader`. | Трейдер с метриками старше 7 дней поставлен на пересчет, дата расчета присутствует в карточке и в MCP-ответе. |
| NFR-4 | Воспроизводимость | Повторный пересчет сохраненных метрик той же версией методики дает идентичные оценку, уверенность и вердикт. Метрики и вердикты не перезаписываются, а добавляются в историю. | Два пересчета одной версии дают совпадающие значения, число записей истории только растет. |
| NFR-5 | Время ответа | Веб-рейтинг, карточка и каждый MCP-инструмент отвечают за p95 <= 2 с при 10 одновременных клиентах. | Нагрузочный тест: 10 параллельных клиентов, 10 минут, p95 <= 2 с для каждой операции. |
| NFR-6 | Надежность доставки | Каждое событие доставляется каждому подписчику ровно один раз: без пропусков и дублей, в том числе при перезапуске системы и при недоступности Telegram до 10 минут. | Перезапуск и 10-минутная недоступность Telegram во время 20 событий: каждый подписчик получил каждое событие ровно один раз. |
| NFR-7 | Безопасность | Система не запрашивает и не хранит ключи и доступ к кошельку пользователя. О пользователе Telegram хранится только идентификатор чата и подписки. MCP-инструменты только читают данные. Токены и секреты не хранятся в репозитории. | Список MCP-инструментов содержит только три инструмента чтения. В хранилище нет полей с ключами или персональными данными, кроме идентификатора чата. Сканер секретов по репозиторию находок не дает. |

### Внешние интерфейсы

- HyperLiquid Info API (чтение): публичный рейтинг (FR-1), состояние счета и позиции (FR-2, FR-9), история счета (FR-2), история сделок (FR-2). Ограничен лимитом веса (NFR-2).
- Telegram Bot API: подписки и уведомления (FR-14...FR-16).
- MCP: инструменты для ИИ-агентов (FR-17...FR-19).
- Веб-браузер: рейтинг, карточка, методика, отчет проверки (FR-11...FR-13, FR-20).
- Мониторинг: экспорт метрик и оповещения (NFR-8).

## Приложение А. Параметры методики по умолчанию

А.1 Предварительный отсев (FR-1).

Все условия одновременно:

- стоимость счета >= $10 000;
- прибыль за все время > 0;
- доходность за все время > 20%;
- оборот за все время >= $1 000 000;
- прибыль на доллар оборота >= 0,2%.

А.2 Фильтры (FR-3).

| Фильтр | Порог |
| --- | --- |
| стаж | >= 90 дней |
| завершенных сделок в окне | >= 10 |
| стоимость счета | >= $10 000 |
| доля ликвидированного объема | <= 5% |
| медианное время удержания | >= 1 ч |

А.3 Оценка (FR-4).

Веса:

- доходность с поправкой на риск 0,30;
- отношение прибыли к убыткам 0,20;
- доля прибыльных сделок 0,15;
- максимальная просадка 0,15;
- средняя доходность сделки 0,10;
- стаж 0,10.

Каждая метрика нормируется линейно от 0 до 1, за границами значение не меняется. Например, для доходности с поправкой на риск пол 0, потолок 2. Границы для остальных метрик публикуются на странице методики (FR-13).

А.4 Уверенность (FR-5).

`clip01(сделок / 40) x clip01(точек истории счета / 60)`, при неполной истории сделок результат умножается на 0,5.

А.5 Стиль (FR-6).

| Стиль | Условие (медианное удержание) |
| --- | --- |
| маркет-мейкер | < 5 мин и >= 200 исполнений в день |
| HFT | < 15 мин |
| внутри дня | < 8 ч |
| свинг | < 5 дней |
| позиционный | >= 5 дней |

А.6 Отбор (FR-7).

- Оценка >= 0,5;
- уверенность >= 0,3;
- стиль внутри дня, свинг или позиционный;
- окно оценки 180 дней;
- N=60 отслеживаемых.
